# clave-dev — self-dev supervisor (v1), дизайн

**Дата:** 2026-07-12
**Статус:** дизайн утверждён как основа; это спека для реализации.
**Имена:** `clave-dev` — продукт; `supervisor` — внутреннее имя компонента.

## 1. Цель и не-цели

**Цель v1.** Дать Clave автономно дорабатывать сам себя под супервайзером: по текстовой
задаче агент (Tandem) правит собственный репозиторий, супервайзер прогоняет
сборку/тесты/линт и наблюдает продукт через pty, и цикл повторяется до прохождения
формальных критериев или лимита раундов. Финал — стоп на человеческом ревью (диф +
отчёт), без коммита и установки.

**Не-цели v1.**
- Нет «живой» само-перезагрузки: правки видны только после rebuild+restart (свойство
  компилируемого бинаря).
- Нет pixel/vision-QA: v1 видит только символьную сетку терминала. Терминал-специфичные
  баги (класс среза футера у правой стены) **вне досягаемости** — это фаза vision (§10).
- Нет авто-коммита / авто-`cargo install`: финализация — ручная.
- Не полностью hands-off: обязательный стоп-гейт перед финалом.

## 2. Архитектура и компоненты

Control plane — **вне репозитория и вне перестраиваемого бинаря**. Всё, что правится
(исходники Clave, свежий бинарь), — объект, а не инструмент управления.

- **supervisor (`clave-dev`)** — внешний оркестратор (Python), живёт рядом с репо,
  исполняется стабильным интерпретатором. Держит петлю, состояние раундов, критерии
  останова, отчёт. Никогда не зависит от свежесобранного Clave.
- **headless-вход в Clave (`clave --run …`)** — неинтерактивный режим, запускающий
  существующий `run_tandem` без TUI и стримящий активность в stdout (контракт — §3).
  Вызывается супервайзером через **known-good** бинарь.
- **observer** — pty-харнесс: гоняет **свежий** `target/release/clave` по сценариям,
  снимает символьную сетку и проверяет assertions (§5). Обобщение сегодняшних
  `scripts/render_check.py` / `drive_*`.
- **Два бинаря, жёстко разделённые** (§6): known-good (инструмент правок) и fresh
  (объект наблюдения).

## 3. Контракт headless-режима (`clave --run`)

Риск с ревью: если `run_tandem` завязан на TUI/терминальные события/интерактивные
prompt-циклы, «тонкая обёртка» распухнет. Поэтому контракт фиксируется явно, а
реализация обязана переиспользовать ЯДРО, а не UI.

**Переиспользование.** `run_tandem` уже общается через `mpsc`-канал `WorkerEvent` и не
принимает `&App` — TUI лишь один потребитель этого потока. Headless-вход = второй
потребитель: создаёт канал, спавнит `run_tandem` (как это делает `start_tandem`), дренит
`WorkerEvent` в stdout, ждёт терминального события. Ни TUI, ни raw-mode, ни интерактива.
Роли/effort берутся из конфига (или флагов), не из живого `App`.

**Инвокация.**
```
clave --run <mode> [--cwd <dir>] [--effort <e>] [--rounds <n>] [--task-stdin] [-- <task>]
```
- `mode` ∈ `{tandem, full}`; v1 — `tandem`.
- Задача: из позиционного аргумента ИЛИ из stdin при `--task-stdin` (длинный фидбек с
  сетками не должен упираться в лимит argv).
- `--cwd` — рабочий каталог (репо/worktree); правки идут туда.

**Потоки.**
- **stdin** — тело задачи при `--task-stdin`; иначе не читается.
- **stdout** — построчный прогресс (активность агента: 🅐/🅒-реплики, tool-use), затем
  **ровно одна машинная финальная строка**: `CLAVE-RUN <json>` с
  `{status, code, provider, usage, ended_reason}`. Супервайзер парсит её.
- **stderr** — диагностика/ошибки процесса.

**Коды выхода.** `0` — тёрн агента завершён штатно; `2` — провайдер не залогинен
(preflight-auth); `3` — сбой провайдера/оркестрации; `1` — прочее. **Важно:** exit `0` =
«агент отработал», НЕ «задача решена». Успешность решения судит **только** супервайзер
(сборка/тесты/observer, §5). Headless сам себя не аттестует.

**Feedback.** Накопленный фидбек (падения прошлого раунда + сетки observer + результаты
assertions) супервайзер собирает в стабильный текстовый **контекст-блок** и передаёт в
задачу следующего раунда через stdin. Формат блока документируется (фиксированные
заголовки: `## Проверки`, `## Экран`, `## Assertions`), чтобы агент читал его единообразно.

**Auth preflight.** headless перед запуском неинтерактивно проверяет логин нужных
провайдеров и при отсутствии — выходит `2`, не пытаясь править.

**Требование к реализации.** Ядро Tandem не должно тянуть в headless ничего из
`runtime.rs`/`render.rs`. Если всплывёт скрытая связь с `App`/TUI — её выносим в
параметры, а не тащим UI в headless.

## 4. Петля

Вход: задача + (опц.) task-специфичные assertions. Один раунд:

1. **implement** — supervisor: `<known-good>/clave --run tandem --cwd <worktree>
   --task-stdin` ← (задача + контекст-блок). Tandem правит исходники в worktree.
2. **checks** — `cargo build`, `cargo test`, `cargo clippy`, `cargo fmt --check` в
   worktree; собрать структурированные результаты (падения/варнинги).
3. **observe** — если `build` ок: сценарии observer на `<worktree>/target/release/clave`
   (§5) → сетки + результаты assertions.
4. **judge** — вычислить критерий останова (§5). Зелёно → выход в отчёт (§7). Иначе —
   собрать контекст-блок и вернуться к шагу 1, пока `round < N` и в рамках бюджета (§8).

Внутри цикла — никаких коммитов/установок.

## 5. Observer: сценарии, assertions, формальный критерий останова

Замечание с ревью: «наблюдение сходится» надо формализовать, иначе агент получает
картинку, а супервайзер сам не знает, когда остановиться.

**Сценарий** = `{ name, steps, captures, assertions }`:
- `steps` — последовательность pty-ввода (клавиши/строки) с паузами;
- `captures` — точки снятия символьной сетки;
- `assertions` — список **машинно-проверяемых** предикатов над сеткой; каждый возвращает
  `pass/fail + сообщение`.

**Примитивы assertions (v1):** `visible(substr)`, `not_visible(substr)`,
`line_matches(regex)`, `no_line_overflows_width`, `clean_exit(code==0)`, `launched`
(виден welcome/композер) и производные. Task-специфичные assertions задаёт человек в
задаче (либо агент предлагает, супервайзер фиксирует). Пример для «убрать рамку `?`»:
`not_visible("Управление")`, `visible("Отправка")`.

**Возврат сценария:** сетки (текст — уходят агенту в фидбек) **и** таблица assertions
(pass/fail — для решения супервайзера).

**Критерий останова (формально).** Раунд успешен ⇔ выполнено ВСЁ:
- `cargo build` — ок;
- `cargo test` — 0 падений;
- `cargo clippy` — 0 варнингов (или ≤ зафиксированного baseline);
- `cargo fmt --check` — чисто;
- **все** assertions активных сценариев — `pass`.

Иначе раунд неуспешен → следующий раунд с фидбеком. Базовые структурные assertions
(`launched`, `clean_exit`, `no_line_overflows_width`) активны всегда; UI-корректность
добавляется task-специфичными assertions. Если у задачи нет UI-assertions — сетка всё
равно показывается агенту, но критерий останова опирается на checks + базовые структурные
assertions.

## 6. Изоляция бинарей и PATH (жёстко)

Ключевое свойство: инструмент правок и объект наблюдения не должны перепутаться.

- **known-good** = абсолютный путь к стабильному `clave` (по умолчанию
  `~/.cargo/bin/clave`). В начале прогона супервайзер:
  - **снимает копию** known-good в приватный temp (`<tmp>/clave-dev/known-good/clave`) и
    работает с копией — чтобы посторонний `cargo install` в ходе прогона не подменил
    инструмент;
  - **логирует идентификацию** (`clave --version`, размер/хэш) в отчёт.
- **fresh** = `<worktree>/target/release/clave` — **только** в сценариях observer.
  Никогда — для оркестрации агента.
- **PATH-гигиена.** Оба бинаря вызываются **по абсолютному пути**, никогда `clave` из
  PATH. Дочерние процессы (cargo, агент, observer) запускаются с окружением, из которого
  исключены `target/release` и `.` (репо), чтобы «голый `clave`» не разрешился во fresh.
  Инвариант проверяется тестом супервайзера (§9).

## 7. Git / worktree-безопасность

Замечание с ревью: `git checkout .` опасен (сносит чужие незакоммиченные правки).
Заменяем на изоляцию.

- **preflight** — основной чекаут должен быть чистым (или явный `--allow-dirty`, тогда
  сначала `git stash` с восстановлением в конце). Грязное дерево без флага → **abort**,
  ничего не трогаем.
- **изолированный worktree** — весь прогон в отдельном
  `git worktree add <tmp>/clave-dev/wt-<ts> <base-ref>`. Агент правит worktree,
  сборка/observer идут там же (свой `target/`). Основной checkout пользователя не
  затрагивается.
- **отчёт** — по завершении: `git -C <worktree> diff` (или ветка), список изменённых
  файлов, результаты checks/assertions, лог версий бинарей. Человек решает: применить/
  смержить или отбросить.
- **отбрасывание** = `git worktree remove` — чисто, без риска для основного дерева.
  Никакого `checkout .` по рабочему каталогу пользователя.

## 8. Обработка ошибок и разгон

- Сбой агента (`--run` код `2/3/1`) → стоп, отчёт с кодом/причиной.
- Разгон → **лимит раундов** `N` + **бюджет** (wall-clock и/или токены из `usage`);
  превышение → стоп с последним состоянием.
- Зависший pty → таймаут сценария (механика уже есть в наших харнессах).
- Флаки-тесты → повтор проверки K раз, пометка нестабильности; не крутить петлю вечно
  из-за мигающего теста.
- Билд не чинится за `N` раундов → стоп, отчёт с последней ошибкой сборки + диф.

## 9. Тестирование супервайзера

- **Юнит:** парсинг результатов cargo (падения тестов, счётчик clippy), парсинг
  `CLAVE-RUN <json>`, снятие сетки и вычисление assertions — на фикстурах (сохранённые
  выводы/сетки).
- **Инвариант изоляции:** тест, что вызовы идут по абсолютному пути и PATH не содержит
  `target/release`/`.` (§6).
- **Смоук end-to-end:** прогон на тривиальной seeded-задаче (напр. «поменяй подпись X»)
  с **мок-провайдерами** (`mock-codex.sh`/`mock-claude.sh` через `CLAVE_CLAUDE`/
  `CLAVE_CODEX`), чтобы проверить механику петли без реальных API-вызовов.

## 10. За рамками v1 (следующие фазы)

- **Фаза 2 — vision:** скриншот реального терминала (в том же эмуляторе, что у
  пользователя) + мультимодальная модель для истинно визуальных багов (класс среза
  футера). Недостижимо символьной сеткой.
- **Фаза 3 — интеграция в продукт:** тонкий Clave-facing запуск (`/self-dev` или
  `clave dev …`), стрим прогресса в TUI — при сохранении control plane снаружи.
- **Прочее:** авто-финализация с сильными гейтами; работа не только над собой (любой
  repo); параллельные кандидаты (несколько worktree, отбор лучшего).
