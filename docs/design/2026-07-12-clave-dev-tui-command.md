# clave-dev — Фаза 3: команда `/dev` в TUI

Статус: дизайн утверждён (направление `/dev <задача>` + 3 уточнения: known-good=current_exe с копией/hash, поиск clave_dev по цепочке, типизированный стрим; и busy-preflight). Следующий шаг после ревью — план и реализация.

Предшественники: Фаза 1 (`docs/design/2026-07-12-clave-dev-supervisor.md`, headless `clave --run` + внешний супервайзер), Фаза 2 (`docs/design/2026-07-12-clave-dev-vision.md`, зрение). Фаза 3 — продуктовая обёртка: TUI даёт удобный **триггер и вид** для внешнего супервайзера, не нарушая инвариант «control plane вне пересобираемого бинаря».

## §1. Цель и не-цели

**Цель.** Команда `/dev <задача>` внутри Clave: запускает внешний `clave-dev` на текущем репозитории, стримит типизированный прогресс в транскрипт, показывает финальный отчёт+диф, останавливается на ревью (без коммита/установки). Тяжёлая и опасная часть (пересборка, worktree, петля) остаётся во внешнем процессе.

**Не-цели (v3).**
- Петля внутри процесса clave — запрещено инвариантом (пересобранный/упавший clave утащил бы супервайзера).
- Автокоммит/автоустановка результата — по-прежнему нет; финал на ревью.
- Параллельные чат и dev-прогон — v3 ведёт `/dev` как прогон агента (busy + cancel), один активный процесс.

## §2. Архитектура (две стороны)

- **Python (супервайзер), доп. работа:** типизированный протокол прогресса (§5) — эмиттер, флаг `--protocol clave-dev`; enhance `snapshot_known_good` (лог hash, §3).
- **Rust (TUI), новое:** обработчик `/dev` в `src/app/commands.rs` (рядом с `/quit`); спавн `python3 -m clave_dev …` в рабочем потоке (переиспуём thread+mpsc+`WorkerEvent`, как у агент-прогона); парсер строк `CLAVE-DEV <type> …` в типизированные события; рендер в транскрипт; отмена через process-group kill; busy-preflight.

Поток: `/dev <task>` → preflight (не занят?) → resolve known-good (§3) + clave_dev (§4) → спавн внешнего процесса с `--protocol clave-dev` → построчный парс stdout в типизированные события → рендер прогресса/проверок/отчёта → стоп на ревью; Ctrl+C убивает process-group.

## §3. known-good = current_exe(), с оговоркой (уточнение 1)

- `/dev` передаёт супервайзеру **абсолютный** путь текущего бинаря — `std::env::current_exe()` (канонизированный), **не** имя из PATH. Работающий бинарь уже стартовал и не зависит от будущей пересборки — корректный эталон с поддержкой `--run`.
- Супервайзер всё равно делает то, что и в Фазе 1: **копирует** этот путь в приватный temp и **логирует идентификацию** — версия (первая строка `--help`) плюс **sha256 бинаря**. Enhance `snapshot_known_good`: добавить поле `hash` в `KnownGood` и считать sha256 скопированного файла; hash идёт в лог/отчёт прогона.
- Смысл: даже если что-то в PATH подменит `clave`, супервайзер работает со своей temp-копией известного бинаря, а hash/version фиксируют, что именно гоняли.

## §4. Поиск пакета clave_dev: цепочка фолбэков (уточнение 2)

`<исходники clave>/tools/clave-dev` из установленного бинаря не всегда выводим. Порядок разрешения (первый успешный):
1. **`CLAVE_DEV_HOME`** — явный путь к каталогу пакета (`tools/clave-dev`). Высший приоритет.
2. **dev-сборка рядом с репо** — `<--repo cwd>/tools/clave-dev`, если существует (самопиление: пакет прямо в репозитории).
3. **Установленный модуль** — `python3 -c "import clave_dev"` успешен (venv/site-packages) → запуск `python3 -m clave_dev` без `PYTHONPATH`.
4. **Иначе — понятная ошибка** в транскрипт: «clave_dev не найден: задай `CLAVE_DEV_HOME`, либо `pip install`, либо запусти из репозитория с `tools/clave-dev`». Не тихий фейл.

Найденный путь (1/2) прокидывается в дочерний процесс через `PYTHONPATH`/cwd; вариант 3 запускается как модуль. `python3` берётся из окружения (в v3 — системный/venv; выбор интерпретатора логируется).

## §5. Типизированный протокол прогресса (уточнение 3)

Супервайзер при `--protocol clave-dev` печатает машинные строки `CLAVE-DEV <type> <payload>` (греппаемо, как `CLAVE-RUN` Фазы 1). Типы v3:
- `CLAVE-DEV progress <text>` — человекочитаемая строка хода (старт раунда, «агент правит…», «сборка…»).
- `CLAVE-DEV check <json>` — результат проверки: `{"name":"build|test|clippy|fmt","ok":bool,"detail":"…"}`.
- `CLAVE-DEV vision <json>` — сводка визуального вердикта (если зрение включено): `{"pass":bool,"issues":n}`.
- `CLAVE-DEV report <json>` — финал: `{"converged":bool,"rounds":n,"max_rounds":n,"worktree":"…","known_good":"…","hash":"…"}`.
- `CLAVE-DEV error <text>` — ошибка (preflight, окно, бэкенд и т.п.).

Rust-сторона парсит префикс и рендерит по типу (progress — строкой, check/vision — со статус-иконкой, report — блоком-сводкой + путь к worktree/дифу, error — выделенно). Человеческий `render_report` остаётся для standalone-CLI (без `--protocol`), чтобы не ломать Фазу 1/2. Эмиссия типизированных строк — additive и не заменяет существующий контракт.

Реализация на Python: тонкий `emitter(type, payload)` пробрасывается в `run_loop`; при `--protocol clave-dev` печатает префиксные строки, иначе — no-op (плюс финальный human-отчёт). Юнит-тест: эмиттер формирует корректные префиксы/JSON.

## §6. TUI: команда, busy-preflight, стрим, отмена

- **Команда** `/dev <задача>` в `src/app/commands.rs`. Пустая задача → подсказка по использованию.
- **Busy-preflight (уточнение 4):** если уже идёт agent- или dev-прогон (`should_quit`/busy-флаг состояния) — `/dev` отвечает «занят, дождись/отмени текущий прогон» и **не** стартует второй процесс.
- **Спавн:** рабочий поток, `Command` с `process_group(0)` (переиспуём инфру критичных фиксов), stdout построчно в канал → `WorkerEvent`. Аргументы: задача, `--repo <cwd>`, `--known-good <abs current_exe>`, `--protocol clave-dev`, проброс конфига (§7).
- **Стрим/рендер:** типизированные строки (§5) → события → транскрипт по мере поступления; финальный `report` — сводка + путь к worktree для ревью дифа.
- **Отмена:** Ctrl+C (как у агента) → `libc::kill(-pid, SIGKILL)` по группе, чтобы не осталось висящих cargo/python.
- **Состояние:** на время прогона — busy (ввод новых команд ограничен, доступна отмена), по завершении — обратно в норму.

## §7. Проброс конфига

Из TUI в `clave-dev` пробрасываются: `--effort <текущий>`, `--rounds <текущие>`, и режим (роли executor/critic) — через уже существующие механизмы супервайзера/headless. Зрение (`--vision`) в v3 по умолчанию выключено (Фаза 2 требует GUI-разрешений); включается явно, если пользователь настроил.

## §8. Ошибки — внятно в транскрипт

- clave_dev не найден (§4) → инструкция, не тихий фейл.
- `python3` отсутствует → понятная ошибка с подсказкой.
- Грязное дерево репо (preflight супервайзера) → сообщение «закоммить/спрячь», прогон не стартует.
- Внешний процесс упал/вернул ненулевой код без `report` → показать `error` и код, не выдавать успех.
- Отмена → корректно снять группу, сообщить «прогон отменён».

## §9. Тестирование и верификация

**Rust (headless здесь, pyte + мок `python3`):**
- `/dev` распознаётся; пустая задача → подсказка.
- busy-preflight: второй `/dev`/agent во время прогона → «занят», второй процесс не стартует.
- спавн: подставной `python3`-скрипт печатает типизированные `CLAVE-DEV …` строки → TUI парсит и рендерит по типам; финальный `report` → сводка.
- отмена: длинный подставной процесс → Ctrl+C снимает группу (нет висящих детей).
- resolve known-good = абсолютный current_exe (не PATH-имя); resolve clave_dev по цепочке §4.

**Python (юнит):** эмиттер типизированных строк; `snapshot_known_good` считает hash.

**Полный e2e (тяжёлый, опционально):** реальный `/dev` на мок-провайдерах — настоящие cargo-сборки из TUI; проверяется вручную.

## §10. Границы и хвост

Фаза 3 закрывает продуктовую интеграцию v1-цикла (Фазы 1–3). Хвостовые идеи отдельными циклами поверх готового: авто-финализация (коммит/PR по approve), работа над произвольным repo как первоклассный сценарий, параллельные кандидаты-решения, выбор интерпретатора/окружения. В main весь self-dev сливается только после завершения и проверки v1-цикла на ветке.
