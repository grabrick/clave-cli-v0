# clave-dev — Фаза 2: vision (реальный macOS-рендер терминала)

Статус: дизайн утверждён (направление + vision-контракт «чеклист + открытая критика» + 4 уточнения). Следующий шаг после ревью спеки — план и реализация.

Предшественник: Фаза 1 (v1) — `docs/design/2026-07-12-clave-dev-supervisor.md` (headless-вход `clave --run` + внешний Python-супервайзер с текстовым pyte-наблюдением). Фаза 2 надстраивается над готовым супервайзером (`tools/clave-dev/`), не переписывая его.

## §1. Цель и не-цели

**Цель.** Дать clave-dev «зрение»: observer, помимо текстовой pyte-сетки, снимает **реальный рендер Terminal.app** (screenshot) и отдаёт его зрячей модели, которая выносит **структурированный вердикт** о визуальных дефектах. Вердикт даёт супервайзеру формальный `pass/fail`, а агенту — пригодный фидбэк (что и где не так). Мотив: класс багов вроде среза последней буквы у правой стенки — это артефакт рендеринга Terminal.app (ambiguous-width), которого pyte не воспроизводит; текстовое наблюдение Фазы 1 его структурно не видит.

**Не-цели (v2).**
- Headless/CI-зрение — отложено: Фаза 2 привязана к GUI и локальна.
- Кроссплатформенность — только macOS + Terminal.app (iTerm2 — опционально позже).
- Замена текстового наблюдения — vision **дополняет** pyte, не заменяет (pyte остаётся дешёвым первым проходом и держит структурные assertions Фазы 1).

**Честное ограничение по верификации.** Реальный e2e (Terminal.app → screenshot → распознавание) запускается **на машине пользователя** с выданными Accessibility + Screen Recording. В headless-сессии проверяются только сборка команд, разрешение окна, парсинг вердикта, интеграция критерия и обработка ошибок (см. §9). Настоящий proof — локальный прогон на заведомо-битом UI.

## §2. Архитектура

Новые модули в `tools/clave-dev/clave_dev/`:
- `terminal_driver.py` — запуск clave в Terminal.app через AppleScript (`osascript`), отправка клавиш (System Events `keystroke`), установка уникального заголовка окна для последующего разрешения.
- `window_resolve.py` — слой «Terminal window → CGWindowID» (§5) c диагностикой «окно не найдено».
- `capture.py` — снимок конкретного окна: `screencapture -x -o -l<CGWindowID> out.png`.
- `terminal_profile.py` — фиксированная терминальная среда (§4): применение и/или логирование columns/rows, шрифта, темы, opacity, bounds, locale.
- `vision.py` — интерфейс `VisionProvider.analyze_image(png, prompt) -> VisionVerdict` (§3) + конкретные реализации, детект возможностей.
- `visual_verdict.py` — схема и парсер `VisionVerdict` (§6).
- Интеграция в существующие `observer.py`/`loop.py`/`context.py` (§7).

Поток одного визуального прохода: `terminal_driver` поднимает clave в Terminal.app с уникальным титулом → `terminal_profile` применяет/логирует среду → драйвер отыгрывает сценарий (клавиши) → `window_resolve` находит CGWindowID → `capture` снимает PNG → `vision` отдаёт PNG модели → `visual_verdict` парсит → observer возвращает вердикт в петлю.

## §3. Контракт vision-провайдера (уточнение 1 — интерфейс, не привязка к текущему провайдеру)

**Не предполагаем**, что текущий текстовый провайдер агента (`claude`/`codex` CLI) умеет принимать PNG. Vision — отдельная способность с явным интерфейсом:

```python
class VisionProvider(ABC):
    def available(self) -> bool: ...
    def analyze_image(self, png_path: Path, prompt: str) -> VisionVerdict: ...
```

- Реализация подбирается **явно** (флаг/конфиг `--vision <backend>`), а не наследуется от провайдера, которым правит код агент.
- Бэкенды взаимозаменяемы: `ClaudeVisionProvider`, `OpenAIVisionProvider` и т.п.
- Если сконфигурированный бэкенд недоступен или text-only → **громкая ошибка** `VisionUnavailableError`, а подключение реального image-бэкенда — **отдельная задача** плана, а не молчаливая деградация.
- Важно: поддерживает ли текущая интеграция `claude` CLI ввод изображения — **не известно и не предполагается**; это способность, которую надо проверить. Интерфейс от этого не зависит: если CLI не умеет картинки, реализуем `analyze_image` через прямой image-API (Claude/OpenAI). Сначала интерфейс — бэкенд подключаемый.
- Порог блокировки задаётся здесь же: какие severity делают `pass=false` для **необязательных** находок; required-пункты чеклиста блокируют безусловно (см. §6).

## §4. Стабильная терминальная среда (уточнение 2 — иначе vision ловит шум)

Фиксируем профиль прогона `TerminalProfile`:
- приложение: Terminal.app;
- геометрия: bounds окна (x,y,w,h) и/или columns×rows;
- шрифт: семейство + размер;
- тема/профиль Terminal.app (имя), opacity;
- locale: `LANG`/`LC_ALL`, `TERM`.

**Минимум (обязательно):** все параметры **логируются** в метаданные прогона и в отчёт — чтобы любой визуальный вывод был атрибутируем, а не «плавал».
**Целевое (предпочтительно):** перед прогоном **активно выставляем** выделенный профиль Terminal.app (напр. профиль `clave-dev`) и bounds окна через AppleScript, приводя среду к детерминированной. План должен реализовать как минимум логирование и стремиться к активной установке bounds+профиля.

Несоответствие фактической среды заявленному профилю (например, не удалось выставить bounds) — предупреждение в отчёт, не молчаливое игнорирование.

## §5. Разрешение окна: AppleScript id ≠ CGWindowID (уточнение 3)

`screencapture -l<id>` требует **реальный CGWindowID** (CoreGraphics), а не AppleScript `id` окна/таба. Поэтому — явный слой разрешения:

- После запуска драйвер задаёт окну **уникальный титул** (напр. `clave-dev <nonce>`).
- `window_resolve` запрашивает список окон через Quartz `CGWindowListCopyWindowInfo(kCGWindowListOptionOnScreenOnly, kCGNullWindowID)` (pyobjc), фильтрует по `kCGWindowOwnerName == "Terminal"` и совпадению титула (`kCGWindowName`) и/или bounds, возвращает `kCGWindowNumber` (это и есть CGWindowID).
- Зависимость: `pyobjc-framework-Quartz` (новая, отметить в плане). Альтернатива-фолбэк, если pyobjc нежелателен: захват по региону `screencapture -R x,y,w,h` из bounds, отдаваемых AppleScript, — CGWindowID тогда не нужен; но основной путь по решению — именно CGWindowID (точное окно, устойчиво к перекрытию/смещению).
- **Диагностика:** 0 совпадений → `WindowNotFoundError` с логом кандидатов; >1 совпадение → та же ошибка с перечислением (не угадываем). Логика разрешения тестируется на фикстурах window-info (найдено / нет / несколько).

## §6. Схема вердикта: не yes/no, а структура (уточнение 4)

Модель возвращает **находки** (`issues`, `checklist_results`, `open_critique`, `raw`). Поле `pass` — **нормализованное, его вычисляет супервайзер**, а не берёт из ответа модели. Чеклист — supervisor-owned и неизменен в прогоне (как active-assertions Фазы 1); каждый пункт помечен `required`.

```json
{
  "pass": false,
  "issues": [
    {"description": "текст футера липнет к правой стенке, срезан 'x'",
     "severity": "high", "region_hint": [0, 690, 800, 24], "source": "checklist"}
  ],
  "checklist_results": [
    {"check": "текст не касается правой границы", "required": true, "passed": false, "note": "срез у правого края"},
    {"check": "нет обрезанных глифов", "required": true, "passed": true, "note": ""},
    {"check": "рамки/бордеры замкнуты", "required": false, "passed": true, "note": ""}
  ],
  "open_critique": "в остальном раскладка ровная",
  "raw": "<сырой ответ модели для отладки>"
}
```

Правило `pass` (вычисляет супервайзер, формально):

```
pass = (нет ни одного required-пункта чеклиста с passed=false)
       AND (нет ни одного open/необязательного finding с severity >= порога)
```

- **Проваленный required-пункт чеклиста блокирует ВСЕГДА** — независимо от severity и даже если модель не завела соответствующий issue или пометила его `low`. Это прямая защита от «required-пункт упал, а прогон прошёл».
- Порог severity (по умолчанию `high`/`medium` → блок; `low` — в фидбэк, не блокирует) применяется к **open-critique и необязательным (`required=false`) находкам**, а не к required-чеклисту. Порог конфигурируем (§3).
- В примере выше: `pass=false`, потому что упал required-пункт «текст не касается правой границы» (и вдобавок есть `high`-issue) — оба пути дают блок.
- `region_hint` (опц.) — bbox проблемной зоны. `source` — `checklist`/`open` (какой проход нашёл).
- Супервайзер решает по нормализованному `pass`; агент получает `issues` + `checklist_results` + `open_critique` как фидбэк. Так закрывается «модель сказала — супервайзер пожал плечами».

Промпт vision-критика гоняет **оба** прохода: фиксированный required-чеклист (регрессии, детерминированно) и открытый вопрос «что ещё не так».

## §7. Интеграция в петлю

- **Observer.** Для каждого сценария после отыгрыша: снимок → `vision.analyze_image` → `VisionVerdict`. pyte-сетка и текстовые assertions Фазы 1 сохраняются как дешёвый первый уровень.
- **Критерий сходимости** (расширение Фазы 1 §5): всё зелёное (build/test/clippy/fmt) И все текстовые assertions pass И `vision_verdict.pass` для всех сценариев.
- **Контекст агенту** (`build_context`): добавляется блок «Визуальные дефекты» — проваленные пункты чеклиста, issues с severity и region_hint, open_critique.
- **Конфиг/деградация.** `--vision <backend>` включает зрение; `--terminal-profile <name>`; пороги severity. Если vision **не** сконфигурирован — Фаза 2 осознанно откатывается к поведению Фазы 1 (текст-онли) с **явной записью в лог**, что зрение выключено (не молчаливый пропуск).

## §8. Ошибки — только громко, никогда не «ложный pass»

- Нет Screen Recording → screencapture даёт пустой/чёрный кадр или ненулевой код → детект (проверка кода + эвристика «кадр не почти-чёрный/пустой») → `ScreenPermissionError` с инструкцией. Не выдаём «pass».
- Нет Accessibility → инъекция клавиш не проходит → детект и ошибка.
- Окно не найдено / неоднозначно → §5.
- Vision-бэкенд недоступен/text-only → §3, отдельная задача.
- Профиль не применился → предупреждение (§4).

## §9. Тестирование

**Юнит (в headless-сессии, можно здесь):**
- сборка AppleScript- и `screencapture`-команд (строки/аргументы) по параметрам;
- разрешение окна: window-info-фикстуры → CGWindowID (найдено / нет / несколько);
- парсинг `VisionVerdict` из JSON модели: валидный, битый, недостающие поля → дефолты/ошибка;
- вычисление `pass` из issues по порогу severity;
- расширенный критерий сходимости с visual-вердиктом (через `FakeVisionProvider` с канонными вердиктами);
- детект пустого/чёрного кадра (нет разрешения);
- `build_context` включает визуальный фидбэк.

**E2e (на машине пользователя, proof):**
- реальный прогон на заведомо-битом UI (искусственно срезанный футер) → vision называет дефект (`pass=false`, issue про правую стенку);
- на чистом UI → `pass=true`;
- документированная выдача Accessibility + Screen Recording и выбор профиля Terminal.app.

## §10. Границы и связь с Фазой 3

Фаза 2 даёт локальное зрение поверх супервайзера. **Фаза 3** (продуктовая интеграция самопиления в TUI) идёт сразу следом (директива пользователя, без паузы) и переиспользует vision-слой: clave оркестрирует скриншот собственного окна. Всё по-прежнему на ветке `worktree-clave-dev-headless`, в main не сливаем до завершения.
